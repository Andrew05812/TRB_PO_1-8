## Что сделано

Консольное приложение на C#/.NET 8. Внешних NuGet-пакетов нет: для SQLite
используется системная библиотека через P/Invoke, JSON/XML/ZIP и хэширование
взяты из стандартной библиотеки .NET. База `filemanager.db` создаётся сама при
первом запуске, там же лежат пользователи, файлы и журнал операций.

Готовый отчёт: `Отчет_Практика1.docx` и `Отчет_Практика1.pdf`.

Соответствие пунктам задания:

| Пункт | Где лежит | Что делает |
|---|---|---|
| 1. Список дисков | `FileManagerApp/DiskService.cs` | `DriveInfo.GetDrives()`, тип, файловая система, метка, общий и свободный объём |
| 2. Работа с файлами | `FileManagerApp/FileOpsService.cs` | создание, чтение, изменение и удаление текстовых файлов |
| 3. JSON и XML | `FileManagerApp/JsonXmlService.cs` | экспорт списка файлов из БД и импорт обратно |
| 4. ZIP | `FileManagerApp/ZipService.cs` | архивация папки и распаковка архива |
| 5. База данных | `FileManagerApp/Db.cs`, `SqliteNative.cs` | таблицы `Users`, `Files`, `Operations`, запросы с параметрами |
| 6. Журнал | `FileManagerApp/FileOpsService.cs`, `JsonXmlService.cs`, `ZipService.cs` | каждая операция пишется в `Operations`, просмотр — пункт 12 меню |

## Как запустить

Нужен .NET SDK 8. SQLite на Windows уже есть в системе (`winsqlite3.dll`).
На Linux нужен пакет `libsqlite3-0`, на macOS библиотека тоже системная.

```bash
cd Практика1_Файловый_менеджер/FileManagerApp
dotnet build
dotnet run
```

При старте программа просит войти или зарегистрироваться. Пароль при вводе
заменяется звёздочками. После входа открывается меню:

```
 1 - Список дисков
 2 - Создать текстовый файл
 3 - Прочитать файл
 4 - Изменить файл
 5 - Удалить файл
 6 - Экспорт моих файлов (из БД) в JSON
 7 - Импорт файлов из JSON
 8 - Экспорт моих файлов (из БД) в XML
 9 - Импорт файлов из XML
10 - Заархивировать папку в ZIP
11 - Распаковать ZIP
12 - Показать журнал действий (из БД)
 0 - Выход
```

## Про SQLite на Windows

В первой версии имя библиотеки было прописано жёстко как `libsqlite3.so.0`.
Это имя из Linux, поэтому на Windows программа падала ещё до старта с
`Unable to load DLL 'libsqlite3.so.0'`. В `SqliteNative.cs` теперь стоит
`NativeLibrary.SetDllImportResolver`, который при первом обращении выбирает
подходящий файл:

- Windows — `winsqlite3.dll` (входит в Windows 10/11), затем `sqlite3.dll`,
  `e_sqlite3.dll`;
- Linux — `libsqlite3.so.0`, затем `libsqlite3.so`;
- macOS — `libsqlite3.dylib`.

Объявления P/Invoke ссылаются на условное имя `sqlite3`, а реальную библиотеку
подставляет resolver. Соглашение вызова — `cdecl`, строки передаются в UTF-8.
Так один и тот же код работает и в Astra Linux в аудитории, и на домашнем
Windows.

## Как хранятся данные

Таблица `Users`: `id`, `username`, `password_hash`, `salt`, `created_at`.
Пароль не хранится в открытом виде: PBKDF2-SHA256, 100 000 итераций,
случайная соль 16 байт, хэш 32 байта. При входе хэши сравниваются через
`CryptographicOperations.FixedTimeEquals`.

Таблица `Files`: `id`, `filename`, `created_at`, `size`, `location`, `owner_id`.
Таблица `Operations`: `id`, `op_time`, `operation_type`, `file_id`, `user_id`,
`details`.

Все SQL-запросы идут через `?` и `sqlite3_bind_*`. Текст запроса с данными
пользователя не склеивается, поэтому подставить SQL-код через имя файла или
логин не получится. При открытии БД включаются `busy_timeout = 5000` и
`foreign_keys = ON`.

## Самопроверка

В приложение встроен режим `--selfcheck`: он создаёт временную папку и
прогоняет все модули без ручного ввода. Если хоть одна проверка не прошла,
процесс завершается с кодом 1.

```bash
dotnet bin/Debug/net8.0/FileManagerApp.dll --selfcheck
```

Проверяется 18 пунктов:

1. вход возвращает того же пользователя, что и регистрация;
2. неверный пароль отклоняется;
3. слишком короткий пароль не регистрируется;
4. файл создаётся на диске;
5. содержимое файла меняется;
6. размер файла обновляется в БД;
7. чужой файл прочитать нельзя;
8. экспорт в JSON создаёт файл;
9. импортированная запись появляется в БД;
10. экспорт в XML создаёт файл;
11. ZIP-архив создаётся;
12. файл из архива распаковывается;
13. архив с путём `../evil.txt` отклоняется;
14. файл не появляется вне папки распаковки;
15. файл удаляется с диска;
16. запись удалённого файла исчезает из БД;
17. в журнале операций есть записи;
18. изменение файла попадает в журнал.

Последняя строка при успехе — `SELFCHECK: все проверки пройдены успешно`.
Этот же режим используется в конвейере из Практики 2 на стадии `test`.

## Что сделано по безопасности

Задание по сути про файловый менеджер, но курс про безопасную разработку,
поэтому закрыты очевидные места:

- пароли — PBKDF2 с солью, а не открытый текст и не голый SHA;
- для несуществующего логина всё равно считается хэш от соли-заглушки, а текст
  ошибки одинаковый — нельзя узнать, какие логины есть в системе;
- чтение, изменение и удаление файла, который уже записан в БД, разрешено
  только его владельцу;
- текстовый файл больше 10 МБ не читается целиком;
- при записи используется `FileShare.None`, чтобы два экземпляра программы не
  перезаписывали один файл одновременно;
- импорт JSON/XML ограничен 5 МБ и 10 000 записей, карточки с некорректными
  путями пропускаются, чужие записи не меняются;
- в XML-парсере запрещены DTD и внешние сущности (`XmlResolver = null`) —
  защита от XXE;
- при распаковке ZIP проверяются абсолютные пути, буквы дисков, выход за
  папку назначения, количество файлов, размер каждого файла, общий размер и
  коэффициент сжатия; недописанные файлы удаляются;
- архив нельзя создать внутри папки, которую архивируем, иначе он начнёт
  включать сам себя.

## Ограничения

Программа консольная и работает только с локальными файлами. Права
разграничиваются по записям в `Files`: файл, который положили в папку вручную
и ещё не занесли в БД, считается общим — иначе менеджер не смог бы открыть
ничего, кроме созданного им самим. SQLite не поддерживает хранимые процедуры,
поэтому вместо них используются подготовленные выражения — это ближайший
аналог и основное требование по защите от SQL-инъекций. Символические ссылки
отдельно не разыменовываются: при необходимости их стоит проверять через
`File.ResolveLinkTarget`. База не шифруется, это локальный учебный вариант.

**Перед ответом запускаю**


**Порядок показа**

1. Регистрирую пользователя, ввожу пароль — он скрывается звёздочками. Показываю меню из 12 пунктов.
2. Пункт 2 — создаю файл, пункт 3 — читаю, пункт 4 — меняю, пункт 12 — показываю журнал операций.
3. Пункт 6 и 8 — экспорт в JSON/XML, пункт 7/9 — импорт. Пункт 10/11 — ZIP.
4. Открываю `SqliteNative.cs` и `Db.cs`: видно, что SQL идёт через `sqlite3_prepare_v2`, а параметры привязываются отдельно.
5. `AuthService.cs` — PBKDF2-SHA256, 100 000 итераций, соль и `FixedTimeEquals`.

**Что говорю**

Это консольный менеджер на .NET 8. Работа с диском, файлами, JSON/XML, ZIP и SQLite разнесена по отдельным классам, а не свалена в `Program.cs`. Пароли не хранятся в открытом виде: используется PBKDF2 с солью и сравнение за постоянное время. Все запросы к БД параметризованы, поэтому SQL-инъекция через имя файла или логин не проходит. При распаковке ZIP проверяются `..`, абсолютные пути и размеры, чтобы не было Zip Slip и zip-бомбы. Проверка `--selfcheck` прогоняет 18 сценариев на временной папке и падает с ненулевым кодом, если что-то сломалось.

**Вопросы, к которым готовлюсь**

- Почему SQLite, а не MySQL/PostgreSQL: для локального учебного приложения не нужен отдельный сервер, а SQL-синтаксис и параметризация те же.
- Почему P/Invoke, а не NuGet-пакет: в проекте пустой `NuGet.Config`, внешние зависимости не нужны; библиотека выбирается под Windows/Linux/macOS.
- Как проверяется владелец файла: в `Files` есть `owner_id`, перед чтением/изменением/удалением сверяется с текущим пользователем.
- Что с гонками: включены `busy_timeout` и `foreign_keys`, уникальность логина проверяет сама БД.

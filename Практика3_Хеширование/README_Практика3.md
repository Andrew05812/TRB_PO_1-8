## Что сделано

Написан собственный переборщик `bruteforce.py` на Python 3.12. Он принимает хэш,
сам определяет алгоритм (SHA-1, MD5, bcrypt, Argon2id) и подбирает пароль двумя
способами: по словарю и по маске. Перебор идёт в нескольких процессах, потому что
`hashlib` в CPython не отпускает GIL и обычные потоки для этой задачи бесполезны.

Программа проверена на всех 16 учебных хэшах из методички. Словарём из 241 пароля
удалось восстановить 12 хэшей: во всех четырёх алгоритмах нашлись `123456`, `apple`
и `Create`, а «сложный» пароль не нашёлся нигде — его просто нет в словаре.
Полный перебор шестизначных чисел по маске `?d?d?d?d?d?d` занял 0,84 с для SHA-1
и 0,77 с для MD5.

Для сравнения собран John the Ripper jumbo в Docker: готовый пакет из Debian не
умеет bcrypt/Argon2 в нужных форматах, а старый образ не понимал `$argon2id$`.
John нашёл те же три пароля из четырёх на каждом алгоритме. На медленных хэшах он
быстрее в 1,9–2,4 раза, потому что считает все четыре хэша сразу и использует
16 потоков OpenMP, тогда как мой переборщик запускает по одному хэшу на восьми
процессах.

## Файлы

- `bruteforce.py` — сам переборщик: словарь, маска, `--lab`, `--selftest`
- `wordlist.txt` — словарь из 241 распространённого пароля
- `parallel_benchmark.py` — замер ускорения на 1, 2, 4 и 8 процессах
- `crack_results.csv` — результаты по 16 хэшам и двум маскам
- `parallel_results.csv` — времена и ускорение по процессам
- `hash_benchmark.py`, `hash_benchmark_results.csv` — скорость одного хэша на ядре
- `run_john.sh`, `john/` — сборка John в Docker, хэши, логи и `john_results.csv`
- `gen_report.py` — собирает `Отчет_Практика3.docx` и PDF из этих CSV

## Как запустить

Зависимости: Python 3.10+ и пакеты из `requirements.txt` (bcrypt, argon2-cffi).
Для сравнения с John нужен Docker, но для самой лабораторной он не обязателен.

```bash
pip install -r requirements.txt

python bruteforce.py --selftest
python bruteforce.py --lab --workers 8
python parallel_benchmark.py
python gen_report.py
```

Проверка одного хэша по словарю:

```bash
python bruteforce.py --hash 7c4a8d09ca3762af61e59520943dc26494f8941b --dict wordlist.txt
```

Перебор по маске (все шесть цифр, восемь процессов):

```bash
python bruteforce.py --hash e10adc3949ba59abbe56e057f20f883e --mask "?d?d?d?d?d?d" --workers 8
```

Сравнение с John (собирает образ при первом запуске, потом около 30 секунд):

```bash
bash run_john.sh
```

Все хэши и пароли в работе учебные, из методички. Программа не предназначена для
запуска по чужим хэшам или реальным учётным записям — это лабораторный стенд.

## Защита

**Перед ответом запускаю**

```powershell
cd "Практика3_Хеширование"
pip install -r requirements.txt
python bruteforce.py --selftest
python bruteforce.py --lab --workers 8
```

Если `--lab` долго из-за bcrypt/Argon2, показываю заранее сохранённые `lab_run.log`, `crack_results.csv` и `parallel_results.csv`.

**Порядок показа**

1. `--selftest`: шесть проверок, в том числе bcrypt и Argon2id на эталонных хэшах.
2. `crack_results.csv`: 16 строк по четырём алгоритмам, найдено 12 паролей.
3. `parallel_results.csv`: ускорение на 1/2/4/8 процессах; отдельно объясняю, почему MD5 ускоряется хуже bcrypt.
4. `John/john_results.csv`: те же хэши, 16 потоков, сравнение времени.
5. В `Отчет_Практика3.docx` или `Отчет_Практика3.pdf` открываю таблицы и вывод про алгоритм/сложность.

**Что говорю**

Переборщик сам определяет SHA-1, MD5, bcrypt и Argon2id по формату хэша, умеет словарь и маску. Для bcrypt и Argon2 параметры берутся из строки хэша. Параллельность сделана процессами, а не потоками: `hashlib` в CPython держит GIL, и потоки не дают ускорения. Для MD5 узкое место — главный процесс, который генерирует и отправляет кандидатов; для Argon2id — память, потому что каждый процесс занимает 64 МБ. John быстрее на медленных хэшах за счёт C, AVX2 и 16 потоков, но находит те же пароли — значит, мой переборщик считает правильно. Главный вывод: стойкость определяется алгоритмом, а не только длиной пароля.

**Вопросы, к которым готовлюсь**

- Почему не GPU: дискретной видеокарты нет, а на CPU bcrypt/Argon2 всё равно упираются в память и итерации.
- Почему bcrypt медленнее MD5 в сотни тысяч раз: cost=10 и соль, много итераций; это и есть цель.
- Почему словарь нашёл «очень сложный» пароль: это слово `Create` из словаря, категория в методичке не гарантирует стойкость.
- Почему 8 процессов, а не 16: 8 физических ядер; гиперпоточность дала бы меньше прироста и мешала замерам.

# Практика 6. Бинарные уязвимости, вариант 3

Номер студенческого билета 23Б0099 заканчивается на 9, поэтому взят вариант 3 —
программа с `printf(argv[1])`. Это не переполнение буфера, а format string
vulnerability (CWE-134), но задание относится к модулю бинарных уязвимостей,
поэтому разбирается именно этот код.

## Файлы

- `src/vuln_variant3.c` — исходный уязвимый код из методички;
- `src/fixed_variant3.c` — исправленный вариант;
- `src/format_write_demo.c` — отдельный стенд для демонстрации записи через `%n`;
- `docker/Dockerfile` — gcc-12, gcc-multilib, gdb, python3;
- `scripts/run_lab.sh` — сборка и базовые запуски;
- `scripts/gdb_session.txt` — сценарий gdb;
- `scripts/find_offset.py`, `scripts/write_demo.py` — подбор смещения и запись;
- `results/` — сохранённые выводы gdb и запусков;
- `Отчет_Практика6.docx`, `Отчет_Практика6.pdf` — отчёт.

## Сборка

```powershell
docker build -t p6-lab docker
docker run --rm -v "${PWD}:/lab" -w /lab p6-lab sh scripts/run_lab.sh
```

`gcc-12` используется потому, что в образе `gcc:12` основной компилятор
`/usr/local/bin/gcc` собран без 32-битной поддержки, а Debian-пакет
`gcc-multilib` ставит рабочий `gcc-12`.

## Отладка

```powershell
docker run --rm -v "${PWD}:/lab" -w /lab p6-lab `
  gdb -q -batch -x scripts/gdb_session.txt
```

Сценарий ставит breakpoint на `main+92` (перед вызовом `printf`), показывает
вершину стека, строку формата, буфер `buffer` с содержимым файла и указатель
`FILE *secret`. Второй запуск с `%p` показывает, что спецификаторы формата
действительно выполняются.

## Что видно на практике

Обычный запуск `./build/vuln hello` печатает `hello`. Запуск с
`%p.%p.%p.%p.%p.%p.%p.%p` печатает значения со стека, среди которых
`0x52434553` и `0x667b5445` — это байты `SECR` и `ET{f` из файла
`/challenge/app-systeme/ch5/.passwd`. То есть через форматную строку
утекает содержимое памяти, которое программа не собиралась показывать.

`format_write_demo.c` читает строку в стековый буфер. Если положить в начало
строки адрес переменной `target` (0x0804c014) и дописать `%4$n`, printf
запишет в `target` число выведенных символов. В `results/fmtwrite_write.txt`
видно, что `%62c%4$n` записывает 0x42, а `%66c%4$n` — 0x46. Это уже
произвольная запись, а не только чтение.

## Исправление

В `fixed_variant3.c` строка формата стала константой:

```c
printf("%s\n", argv[1]);
```

Дополнительно проверяются `argc`, результат `fopen` и `fgets`. Символы `%`
в аргументе теперь выводятся как обычный текст, что видно в
`results/runs_basic.txt`. Для похожего кода стоит включать
`-Wformat-security` и `-D_FORTIFY_SOURCE=2`, а также не отключать PIE,
stack protector и ASLR в реальной сборке. В лабораторной они отключены
намеренно, чтобы адреса в gdb были предсказуемыми.

## Ограничения

- Все запуски выполняются в локальном контейнере, файл с «секретом» —
  учебный (`SECRET{format_string_lab}`).
- ASLR внутри контейнера полностью отключить не удалось (gdb пишет
  `Operation not permitted`), поэтому адреса стека меняются от запуска
  к запуску. На вывод это не влияет: смещение `%4$n` и адрес `target`
  фиксированы, потому что бинарник собран с `-no-pie`.
- Это учебный пример; никакие реальные программы и системы не затрагивались.

## Защита

**Перед ответом запускаю**

```powershell
cd "Практика6_Бинарные_уязвимости"
docker build -t p6-lab docker
docker run --rm -v "${PWD}:/lab" -w /lab p6-lab sh scripts/run_lab.sh
docker run --rm -v "${PWD}:/lab" -w /lab p6-lab gdb -q -batch -x scripts/gdb_session.txt
```

**Порядок показа**

1. Называю вариант: билет 23Б0099 заканчивается на 9, поэтому вариант 3 — `printf(argv[1])`.
2. Показываю `src/vuln_variant3.c`: файл читается в `buffer[32]`, но `printf` получает `argv[1]` как формат.
3. В выводе `run_lab.sh` показываю `%p`: среди значений есть `0x52434553` и `0x667b5445` — фрагменты `SECRET` из буфера.
4. Показываю `results/fmtwrite_write.txt`: `%62c%4$n` записывает в `target` 0x42, `%66c%4$n` — 0x46.
5. Запускаю исправленную версию с теми же `%p` — они печатаются как текст.
6. В gdb показываю breakpoint перед `printf`, `x/s` для строки формата и `x/40bx $ebp-0x3c` для буфера.

**Что говорю**

Это не переполнение буфера, а format string vulnerability (CWE-134). `printf` получает пользовательский ввод как программу форматирования: `%p` читает слово со стека, `%s` разыменовывает указатель, `%n` записывает число по адресу. В варианте 3 есть и утечка, и потенциальная запись. На отдельном стенде я показал запись в глобальную переменную, чтобы не зависеть от версии libc. Исправление — `printf("%s", argv[1])`: формат становится константой, ввод остаётся данными. Дополнительно добавил проверки `argc`, `fopen` и `fgets`, а для реальной сборки — `-Wformat-security`, PIE, stack protector и ASLR.

**Вопросы, к которым готовлюсь**

- Почему собран 32-битным и без PIE: короче адреса, в gdb нагляднее, адрес `target` фиксирован; это только для лабораторной.
- Почему `%n` опаснее `%p`: `%p` только читает, `%n` пишет по адресу и может испортить управляющий поток.
- Почему ASLR не отключился: в контейнере нет прав на `personality`; адреса стека меняются, но смещение `%4$n` и `target` фиксированы.
- Почему `printf("%s", argv[1])` достаточно: строка формата больше не зависит от ввода, спецификаторы не выполняются.
